# Codex CLI + Kimi Code marketplace support

## Problem

This repo already ships a native Claude Code marketplace
(`.claude-plugin/marketplace.json`, generated by
`scripts/generate-manifests.mjs` from `skills/*/SKILL.md`
frontmatter). Codex CLI and Kimi Code each have their own, structurally
different plugin/marketplace mechanisms, and neither is currently
supported — users of those agents can only install skills through the
generic `npx skills` cross-agent installer or a manual copy.

## Goal

Add native marketplace support for Codex CLI and Kimi Code, generated
from the same `skills/*/SKILL.md` frontmatter that already drives the
Claude manifest, so all three agents get first-class
`/plugin marketplace add` / `/plugins marketplace` install paths with
per-skill install granularity.

## Schemas (source of truth)

**Codex CLI** — grounded in the official spec shipped in
[`openai/codex`](https://github.com/openai/codex/blob/main/codex-rs/skills/src/assets/samples/plugin-creator/references/plugin-json-spec.md):

- Repo-root catalog: `.agents/plugins/marketplace.json`
  ```json
  {
    "name": "ake-skills",
    "interface": { "displayName": "ake-skills" },
    "plugins": [
      {
        "name": "ake-skills",
        "source": { "source": "local", "path": "./" },
        "policy": { "installation": "AVAILABLE", "authentication": "ON_USE" },
        "category": "Productivity"
      },
      {
        "name": "<skill>",
        "source": { "source": "local", "path": "./skills/<skill>" },
        "policy": { "installation": "AVAILABLE", "authentication": "ON_USE" },
        "category": "Productivity"
      }
    ]
  }
  ```
- Per-plugin manifest: `.codex-plugin/plugin.json` at repo root (the
  bundle) and inside every `skills/<name>/` (the individual skill).
  Required fields: `name`, `version`, `description`, `author.name`,
  `interface.displayName`, `interface.shortDescription`,
  `interface.longDescription`. `skills` is `"./skills"` for the bundle
  plugin, `"./"` for each individual skill plugin.
  - `displayName` ← title-cased skill name
  - `shortDescription` ← first sentence of the SKILL.md description
  - `longDescription` ← full SKILL.md description

**Kimi Code** — grounded in the official docs in
[`MoonshotAI/kimi-code`](https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/customization/plugins.md):

- Repo-root catalog: `marketplace.json`
  ```json
  {
    "version": "2",
    "plugins": [
      { "id": "ake-skills", "displayName": "ake-skills", "source": "./" },
      { "id": "<skill>", "displayName": "<Skill>", "source": "./skills/<skill>" }
    ]
  }
  ```
- Per-plugin manifest: `kimi.plugin.json` at repo root (the bundle)
  and inside every `skills/<name>/` (the individual skill). Fields:
  `name` (must match `^[a-z0-9][a-z0-9_-]{0,63}$` — already guaranteed
  by the existing skill-name validation), `version`, `description`,
  `skills` (`"./skills/"` for the bundle, `"./"` per skill),
  `interface.displayName`, `interface.shortDescription`.

Both agents derive every field from the same two SKILL.md frontmatter
fields (`name`, `description`) plus `VERSION` and the fixed `author`
already used for Claude — no new source of truth, no per-skill
metadata to maintain.

**Fixed defaults** for fields with no SKILL.md equivalent (flat across
all skills, revisit only if a real need for per-skill variance shows
up): Codex `category: "Productivity"`,
`policy.installation: "AVAILABLE"`, `policy.authentication: "ON_USE"`.

**Fidelity caveat**: this is implemented against the documented specs
above; it has not been install-tested against real Codex CLI or Kimi
Code binaries. Worth calling out in the README as best-effort until
someone verifies with the actual CLIs.

## Generator architecture

Three standalone scripts, one per agent — kept separate (not merged
into `generate-manifests.mjs`) so each agent's manifest shape and
file-writing logic stays independently readable and testable:

- `scripts/generate-manifests.mjs` — unchanged, Claude only.
- `scripts/generate-codex-manifests.mjs` — new.
- `scripts/generate-kimi-manifests.mjs` — new.

All three need the same input primitives that `generate-manifests.mjs`
already implements: frontmatter parsing, skill validation, `VERSION`
reading. To avoid three copies of that parsing logic drifting apart,
extract `parseFrontmatter`, `loadSkills`, `validateSkill`,
`readVersion` into `scripts/lib/skills.mjs`; all three generators
import from there. `generate-manifests.mjs` is refactored to import
from the shared lib too (behavior and output unchanged — verified by
its existing test suite continuing to pass unmodified).

Each new generator gets its own test file
(`scripts/generate-codex-manifests.test.mjs`,
`scripts/generate-kimi-manifests.test.mjs`), unit-testing the exported
builder functions the same way `generate-manifests.test.mjs` does
today — not just an end-to-end run.

## CI wiring

`.github/workflows/validate.yml`:

- Test step broadens from the single Claude test file to
  `node --test scripts/*.test.mjs`.
- Two new "regenerate" steps run `generate-codex-manifests.mjs` and
  `generate-kimi-manifests.mjs` before the existing drift check.
- The existing drift gate (`git add -A && git diff --cached
  --exit-code`) already covers any generated file and needs no
  change beyond running after all three generators.

## Out of scope

- Per-skill `category` in SKILL.md frontmatter (flat default for now).
- Install-testing against real Codex/Kimi binaries (not available in
  this environment).
- Any change to the existing `npx skills` / Gemini CLI install paths.
